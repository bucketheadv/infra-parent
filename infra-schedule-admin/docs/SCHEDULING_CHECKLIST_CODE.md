# Infra Schedule 调度系统检查清单

用于上线前评审、版本发布和日常故障演练。每项都应标记负责人、验证时间和结果。

## 1. 基础配置与数据一致性

- [ ] 所有调度中心实例使用同一个 MySQL 数据库，字符集为 `utf8mb4`。
- [ ] 数据库时区、应用时区和业务时区已统一，时间字段均按 Unix 毫秒解释。
- [ ] 已执行最新 schema 和增量迁移，`infra_schedule_job`、`infra_schedule_executor`、`infra_schedule_execution_log` 索引齐全。
- [ ] 所有表主键为自增 `BIGINT`；任务的 `executor_id` 指向执行器自增 ID。
- [ ] 执行器分组标识与实例标识的唯一约束符合设计，展示名称不承担唯一性。
- [ ] 调度中心节点 `scheduler-id` 稳定且唯一，不能使用每次启动都变化的随机值。
- [ ] 调度中心、执行器、管理 API 的访问令牌已通过密钥管理系统注入，未写入代码和日志。
- [ ] 数据库连接池大小、连接超时、事务超时已按调度并发量配置。
- [ ] MySQL 版本支持 `FOR UPDATE SKIP LOCKED`；不支持时已验证替代抢占方案。

## 2. 分布式调度与分页抢占

- [ ] 多个调度中心实例可同时运行，任务不会在同一租约窗口被重复领取。
- [ ] 到期任务查询使用稳定排序（通常为 `next_trigger_at, id`），分页大小和单轮最大页数已压测。
- [ ] 领取任务、写入 `claim_owner/claim_until` 在同一事务内完成。
- [ ] 事务提交后才异步调用执行器，数据库行锁不会覆盖整个任务执行过程。
- [ ] 调度节点宕机后，租约在 `claim_until` 到期后可被其他节点重新领取。
- [ ] 节点时钟偏差已监控；NTP 同步正常，避免租约提前或延迟失效。
- [ ] 任务执行时间超过租约时，已验证不会因租约过短造成重复执行；必要时启用租约续期或调大租约。
- [ ] 任务定义更新、暂停、删除与正在领取的任务并发发生时，旧节点不能覆盖新配置。
- [ ] 领取失败、更新行数异常、数据库死锁均有重试、告警和可检索日志。
- [ ] 已完成双节点/三节点并发调度演练，核对同一 `job_id + trigger_time` 的执行次数。

## 3. 执行器注册、心跳与网络

- [ ] 执行器上报的实例唯一标识稳定，重启不会意外创建大量重复实例。
- [ ] 自动注册地址会随心跳更新，超时实例会从可路由列表剔除。
- [ ] 手动地址不会被自动心跳覆盖；切换地址模式时旧地址已清理。
- [ ] 心跳接口与任务执行接口已配置鉴权、限流和来源控制。
- [ ] 调度中心到执行器的 DNS、端口、防火墙和反向代理超时已验证。
- [ ] 执行器优雅停机会停止接收新任务，并等待或取消进行中的任务。
- [ ] 执行器恢复上线后，心跳、地址注册和任务接收均能自动恢复。
- [ ] 执行器不可达、返回 4xx/5xx、连接超时和响应超时分别有明确的失败状态和告警。

## 4. 路由策略

- [ ] `FAILOVER`：首节点失败后会按候选顺序切换，并限制切换次数。
- [ ] `BUSYOVER`：能识别执行器忙碌状态，避免把任务持续发送到已饱和节点。
- [ ] `FIRST/LAST`：排序规则稳定，不依赖数据库无序返回。
- [ ] `ROUND`：轮询游标在多调度节点间共享或具备可接受的局部性。
- [ ] `RANDOM`：随机分布经过压测，不会长期倾斜到单节点。
- [ ] `CONSISTENT_HASH`：路由键稳定，节点增删时迁移范围符合预期。
- [ ] `LEAST_FREQUENTLY_USED` / `LEAST_RECENTLY_USED`：统计数据有过期、初始化和并发更新处理。
- [ ] `SHARDING_BROADCAST`：分片总数、分片下标和失败汇总均可审计；部分节点失败不会被误报为全成功。
- [ ] 没有健康候选节点时，任务日志明确记录原因，不会忙循环重试。
- [ ] 路由选择使用执行器数据库 ID/地址的类型化字段，不依赖展示名称。

## 5. 阻塞策略与并发控制

- [ ] `SERIAL`：同一任务已有执行时，新触发被串行化或明确跳过。
- [ ] `DISCARD_LATER`：后续触发被丢弃并写入 `SKIPPED` 日志，不能无限积压。
- [ ] `COVER_EARLY`：能够中断旧执行；任务处理器正确响应线程中断和取消信号。
- [ ] 手动触发与定时触发使用相同的并发控制规则，避免绕过阻塞策略。
- [ ] 超时任务会取消调用、记录 `TIMEOUT`，并防止同一任务的线程无限增长。
- [ ] 重试只针对可重试错误；重试次数、间隔和总耗时有上限。
- [ ] 任务幂等性已确认：重复投递、网络重试或节点故障不会造成不可逆业务损坏。
- [ ] 外部副作用（消息、支付、写库）具备幂等键或去重机制。

## 6. 调度日志、清理与僵尸进程

- [ ] 日志状态机完整：`QUEUED → RUNNING → SUCCESS/FAILED/TIMEOUT/SKIPPED/CANCELLED/LOST`。
- [ ] 每条日志包含 `job_id`、触发时间、执行器 ID、目标地址、耗时和错误摘要。
- [ ] 业务过程日志有大小上限、截断策略和敏感信息脱敏规则。
- [ ] 已配置日志保留周期、归档策略和分批删除窗口，删除不会长时间锁表。
- [ ] 清理任务按主键范围或时间索引分页删除，避免一次性 `DELETE` 全表。
- [ ] 清理前确认保留在线上审计、合规和故障追踪所需的最短周期。
- [ ] 定期扫描长时间处于 `QUEUED/RUNNING` 的日志，结合目标地址探活和超时阈值判定僵尸任务。
- [ ] 僵尸日志回收为 `LOST` 或 `FAILED` 时保留原因、发现时间和回收节点。
- [ ] 调度中心重启、执行器强杀、网络分区后，僵尸回收流程均已演练。
- [ ] 清理和回收任务本身具备分布式互斥，不能被多个节点重复执行造成告警风暴。
- [ ] 监控日志表增长率、清理延迟、僵尸数量和回收失败数。

## 7. 常驻任务（Resident Jobs）

- [ ] 常驻任务的业务目的、允许并发数、最大运行时长和退出条件已明确。
- [ ] 常驻任务不会因为正常长时间运行被误判为僵尸；阈值按任务配置覆盖默认值。
- [ ] 常驻任务被暂停、删除或发布新版本时，有取消信号和优雅退出流程。
- [ ] 常驻任务异常退出后是否自动拉起已明确，并设置最大重启频率和熔断窗口。
- [ ] 常驻任务不会重复创建消费者、定时器或线程池；重启后资源可回收。
- [ ] 常驻任务的心跳、处理速率、积压量、最后进度和重启次数可观测。
- [ ] 常驻任务与普通 Cron 任务的日志、告警和清理规则已区分。

## 8. 失败恢复与运维演练

- [ ] MySQL 主从切换、短暂断连、死锁和连接池耗尽均有恢复验证。
- [ ] 调度中心单节点宕机、全体重启和滚动发布不会丢失任务计划。
- [ ] 执行器单节点宕机、批量宕机和网络隔离时，路由与告警符合预期。
- [ ] 应用发布期间任务不会重复执行或长期卡在运行中。
- [ ] 备份包含任务定义、执行器配置和必要的审计日志；恢复演练可在目标时间内完成。
- [ ] 所有关键指标和告警都有负责人、阈值、升级路径和处理手册链接。
